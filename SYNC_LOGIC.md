# Логика синхронизации - Все сценарии

> **Безопасность:** единственный источник правды для продакшена — [`firestore.rules`](firestore.rules) в корне репозитория.
> Не публикуйте правила вида `allow read, write: if request.auth != null` и не копируйте устаревшие примеры из этого файла.

## Правила Firestore

Актуальные правила описаны в [`firestore.rules`](firestore.rules) и проверяются через `firestore-rules-tests/`.
Ниже сохранены только исторические заметки; **не деплойте** примеры из раздела «Временные правила».

### Временные правила (УСТАРЕЛО — только для справки)

**ВАЖНО:** Эти правила полностью открыты для авторизованных пользователей. Используются только для отладки.

```javascript
rules_version = '2';

service cloud.firestore {
  match /databases/{database}/documents {
    function isAuth() { 
      return request.auth != null; 
    }

    match /families/{familyId} {
      // Временные правила: для авторизованных пользователей все разрешено
      allow read, create, update, delete: if isAuth();

      match /members/{memberId} {
        allow read, create, update, delete: if isAuth();
      }

      match /{collection}/{docId} {
        allow read, create, update, delete: if isAuth();
      }
    }
  }
}
```

**Примечание:** Правила не проверяют роли и права, но клиентская логика контролирует доступ (проверка `isMemberWriteAllowed` для записи members).

### Рекомендуемые правила для продакшена

**КРИТИЧНО:** Эти правила должны быть применены перед релизом в продакшен. Без них система уязвима.

```javascript
rules_version = '2';

service cloud.firestore {
  match /databases/{database}/documents {
    
    function isAuth() { 
      return request.auth != null; 
    }

    function memberDoc(f, u, db) { 
      return /databases/$(db)/documents/families/$(f)/members/$(u); 
    }

    function memberExists(f, u, db) { 
      return exists(memberDoc(f, u, db)); 
    }

    function myRole(f, db) {
      // Безопасная проверка: если документа нет, возвращаем null
      return memberExists(f, request.auth.uid, db)
        ? get(memberDoc(f, request.auth.uid, db)).data.role
        : null;
    }

    function isAdmin(f, db) { 
      return myRole(f, db) == 'ADMIN'; 
    }

    match /families/{familyId} {
      // Документ семьи: разрешаем чтение и создание авторизованным пользователям
      allow read, create: if isAuth();

      match /members/{memberId} {
        // Чтение: все авторизованные пользователи могут читать участников
        allow read: if isAuth();

        // Создание/обновление себя как ADMIN при создании семьи
        // Разрешаем если:
        // 1. Пользователь создаёт/обновляет свою запись
        // 2. Роль = ADMIN
        // 3. Либо записи нет (первое создание), либо текущая роль = ADMIN
        allow create: if isAuth()
          && request.auth.uid == memberId
          && request.resource.data.role == 'ADMIN'
          && !memberExists(familyId, memberId, database);

        allow update: if isAuth()
          && request.auth.uid == memberId
          && request.resource.data.role == 'ADMIN'
          && memberExists(familyId, memberId, database)
          && myRole(familyId, database) == 'ADMIN';

        // Заявка: пользователь может создать/обновить только свою запись в роли PENDING
        allow create, update: if isAuth()
          && request.auth.uid == memberId
          && request.resource.data.role == 'PENDING'
          && (!memberExists(familyId, memberId, database) || myRole(familyId, database) == 'PENDING');

        // Обновление своей записи (для изменения имени, аватара и т.д.)
        // Но НЕ роли (роль может менять только админ)
        allow update: if isAuth()
          && request.auth.uid == memberId
          && memberExists(familyId, memberId, database)
          && request.resource.data.role == resource.data.role;  // Роль не меняется

        // Админ может создавать/обновлять/удалять любых участников
        allow create, update, delete: if isAuth() && isAdmin(familyId, database);
      }

      // Все прочие коллекции семьи (tasks, shopping, events и т.д.)
      // ВАЖНО: batch.set() может быть как create, так и update
      // Поэтому разрешаем и create, и update явно
      match /{collection}/{docId} {
        allow read: if isAuth() && collection != "members";
        allow create: if isAuth() && collection != "members";
        allow update: if isAuth() && collection != "members";
        allow delete: if isAuth() && collection != "members";
      }
    }
  }
}
```

**Ключевые ограничения для продакшена:**
- Только первый пользователь может создать себя как ADMIN (если записи нет)
- Пользователь может создать/обновить себя только как PENDING (заявка)
- Админ может создавать/обновлять/удалять любых участников
- Не-админы НЕ могут писать в members (кроме своей записи как PENDING)
- Роль можно менять только админу (кроме создания себя как ADMIN)
- **КРИТИЧНО: В семье может быть только один ADMIN** (проверка на клиенте, см. раздел "Лимит на единственного админа")

## Состояния участника

### Локальное состояние:
- `role`: ADMIN, PARENT, CHILD, PENDING
- `inLocalDB`: есть/нет в локальной БД
- `dataCleared`: данные очищены (только личные цели остались)

### Удаленное состояние (remote):
- `inRemote`: есть/нет в remote
- `remoteRole`: ADMIN, PARENT, CHILD, PENDING, null

### Служебные флаги:
- `deletedMembers`: список ID участников, удаленных админом
- `syncEnabled`: синхронизация включена/выключена

## Клиентская логика контроля доступа

### Запрет записи members для не-админов

**КРИТИЧНО:** Даже при открытых правилах Firestore (временные правила), клиентская логика строго контролирует доступ к записи в коллекцию `members`.

**Реализация:**

1. **Флаг `isMemberWriteAllowed`** определяется в `syncNow`:
   - `true` только если пользователь ADMIN в remote (или создает новую семью как ADMIN)
   - `false` для всех остальных ролей (PARENT, CHILD, PENDING)

2. **`uploadSnapshot` в `FirestoreBackendApi`** использует `isMemberWriteAllowed`:
   ```kotlin
   if (isMemberWriteAllowed) {
       syncCollection(MEMBERS_COLLECTION, snapshot.members, ExportMember::id)
   }
   ```
   - Если `isMemberWriteAllowed = false`, участники **НЕ записываются** в batch
   - Только админ может записывать/обновлять/удалять участников через `uploadSnapshot`

3. **`publishSelfMember`** позволяет не-админам только:
   - Создать себя как ADMIN (при создании новой семьи)
   - Создать/обновить себя как PENDING (при подаче заявки)
   - Обновить свою запись (имя, аватар) без изменения роли

**Результат:**
- Не-админы физически не могут записать других участников в members
- Даже если правила Firestore разрешают, клиентская логика блокирует это
- В продакшене правила Firestore дополнительно защищают на уровне сервера

**Двойная защита:**
1. Клиентская логика (`isMemberWriteAllowed`) - блокирует на уровне кода
2. Правила Firestore (в продакшене) - блокируют на уровне сервера

## Сценарии

### 1. СОЗДАНИЕ НОВОЙ СЕМЬИ

**Условия:**
- `remoteData == null || remoteData.members.isEmpty()`
- Локально пользователь ADMIN (или создается как ADMIN)

**Действия:**
1. Очистить `deletedMembers` (новая семья = новый контекст)
2. Отправить себя как ADMIN на сервер
3. Синк включен
4. Данные не очищаются

**Результат:**
- На сервере: один участник с ролью ADMIN
- Локально: один участник с ролью ADMIN
- Синк: включен

---

### 2. ПРИСОЕДИНЕНИЕ К СУЩЕСТВУЮЩЕЙ СЕМЬЕ (первая попытка)

**Условия:**
- `remoteData != null && remoteData.members.isNotEmpty()`
- `currentUserId !in remoteData.members`
- Локально пользователь PENDING (или создается как PENDING)

**Действия:**
1. Отправить себя как PENDING на сервер
2. Синк включен
3. НЕ импортировать данные семьи (только читать состав участников)
4. НЕ отправлять свои данные (tasks, events и т.д.)

**Результат:**
- На сервере: новый участник с ролью PENDING
- Локально: пользователь с ролью PENDING
- Синк: включен
- Данные: не импортируются, не отправляются

---

### 3. ОДОБРЕНИЕ ЗАЯВКИ АДМИНОМ

**На устройстве админа:**
- Админ видит PENDING участника
- Админ меняет роль на PARENT/CHILD
- Изменение сохраняется локально и отправляется на сервер

**На устройстве ожидающего:**
- При следующей синхронизации:
  - `remoteRole != PENDING && localRole == PENDING`
  - Принять роль из remote (PARENT/CHILD)
  - Начать импорт данных семьи
  - Начать отправку своих данных
  - Удалить из `deletedMembers` (если был там)

**Результат:**
- На сервере: участник с ролью PARENT/CHILD
- Локально (ожидающий): роль обновлена на PARENT/CHILD
- Синк: включен
- Данные: начинают синхронизироваться

---

### 4. ОТКЛОНЕНИЕ ЗАЯВКИ АДМИНОМ

**На устройстве админа:**
- Админ видит PENDING участника
- Админ нажимает "Отклонить"
- Участник удаляется с сервера (`deleteMemberFromServer`)
- Участник добавляется в `deletedMembers`
- Участник удаляется локально у админа

**На устройстве отклоненного:**
- При следующей синхронизации:
  - `!isInRemote && remoteData != null`
  - `localRole == PENDING` (или другая роль)
  - Очистить данные семьи (кроме личных целей)
  - Установить роль PENDING
  - Добавить в `deletedMembers` (если еще не там)
  - НЕ отключать синк
  - Показать сообщение "Ваша заявка отклонена"
  - НЕ отправлять заявку автоматически

**Результат:**
- На сервере: участника нет
- Локально (отклоненный): роль PENDING, данные очищены
- Синк: включен (но заявка не отправляется)
- `deletedMembers`: содержит ID отклоненного

---

### 5. УДАЛЕНИЕ УЧАСТНИКА АДМИНОМ (не PENDING)

**На устройстве админа:**
- Админ удаляет участника (PARENT/CHILD)
- Участник удаляется с сервера
- Участник добавляется в `deletedMembers`
- Участник удаляется локально у админа

**На устройстве удаленного:**
- При следующей синхронизации:
  - `!isInRemote && remoteData != null`
  - `localRole != PENDING` (PARENT/CHILD)
  - Очистить данные семьи (кроме личных целей)
  - Установить роль PENDING
  - Добавить в `deletedMembers`
  - НЕ отключать синк
  - Показать сообщение "Вы были удалены из семьи"
  - НЕ отправлять заявку автоматически

**Результат:**
- На сервере: участника нет
- Локально (удаленный): роль PENDING, данные очищены
- Синк: включен (но заявка не отправляется)
- `deletedMembers`: содержит ID удаленного

---

### 6. ПОВТОРНАЯ ПОДАЧА ЗАЯВКИ ПОСЛЕ ОТКЛОНЕНИЯ

**Условия:**
- Пользователь в `deletedMembers`
- Локально роль PENDING
- На сервере участника нет

**Действия (явное действие пользователя):**
1. Пользователь нажимает "Повторно подать заявку" (UI)
2. Вызвать `publishSelfMember(accountId, forceResubmit = true)`
3. Удалить из `deletedMembers`
4. Отправить себя как PENDING на сервер

**Результат:**
- На сервере: участник с ролью PENDING (новая заявка)
- Локально: роль PENDING
- Синк: включен
- `deletedMembers`: не содержит ID (удален)

**Важно:** Если пользователь НЕ в `deletedMembers`, но его нет в remote и он PENDING - это первая попытка присоединения, отправляем заявку.

---

### 7. СИНХРОНИЗАЦИЯ В РАЗЛИЧНЫХ СОСТОЯНИЯХ

#### 7.1. Админ синхронизируется

**Поведение:**
- Может читать и писать всех участников
- Видит новых PENDING участников из remote
- Может удалять участников
- Удаленные участники не восстанавливаются из remote (проверка `deletedMembers`)

#### 7.2. PENDING участник синхронизируется

**Поведение:**
- Если `inRemote && remoteRole == PENDING`: ждет одобрения, не импортирует данные, не отправляет данные
- Если `inRemote && remoteRole != PENDING`: принят, начинает импорт данных
- Если `!inRemote && inDeletedMembers`: отклонен, не отправляет заявку автоматически
- Если `!inRemote && !inDeletedMembers`: может отправить заявку (первая попытка или явная повторная)

#### 7.3. PARENT/CHILD участник синхронизируется

**Поведение:**
- Импортирует данные семьи
- Отправляет свои данные
- Если `!inRemote`: был удален, очистить данные, установить PENDING

## Правила обработки конфликтов

### Правило 1: Приоритет remote для ролей (кроме PENDING)
- Если `remoteRole != PENDING && localRole == PENDING`: принять remoteRole (одобрено)
- Если `remoteRole == PENDING && localRole != PENDING`: не отправлять localRole (ждем одобрения)

### Правило 2: Защита от перезаписи ADMIN
- Если `remoteRole == ADMIN && localRole == PENDING`: не отправлять PENDING (защита от перезаписи)

### Правило 3: Список удаленных участников
- Админ добавляет в `deletedMembers` при отклонении/удалении
- Участник в `deletedMembers` не может автоматически отправить заявку
- Участник удаляется из `deletedMembers` только при:
  - Явной повторной подаче заявки (`forceResubmit = true`)
  - Одобрении админом (когда `remoteRole != PENDING`)

### Правило 4: Очистка данных
- Данные очищаются только когда: `!inRemote && remoteData != null`
- Очищаются: все данные семьи, кроме личных целей и Awesomeness
- После очистки: роль устанавливается в PENDING

### Правило 5: Синк не отключается автоматически
- Синк отключается только при:
  - Явном выходе пользователя из семьи
  - Удалении семьи полностью
- Синк НЕ отключается при:
  - Отклонении заявки
  - Удалении участника

## Критические проверки

### В `publishSelfMember`:
1. Если `remoteData == null || remoteData.members.isEmpty()`: создание новой семьи → отправить роль как есть (ADMIN)
2. Если `remoteMember == null`:
   - Если `inDeletedMembers && !forceResubmit`: НЕ отправлять
   - Если `inDeletedMembers && forceResubmit`: удалить из списка, отправить PENDING
   - Если `!inDeletedMembers && role == PENDING`: отправить PENDING (первая попытка)
   - Если `role != PENDING`: НЕ отправлять (syncNow обработает очистку)
3. Если `remoteMember != null`:
   - Если `remoteRole == ADMIN && localRole == PENDING`: НЕ отправлять (защита)
   - Если `localRole == PENDING && remoteRole != PENDING`: НЕ отправлять (одобрено)
   - Если `localRole != PENDING && remoteRole == PENDING`: НЕ отправлять (ждем одобрения)
   - Иначе: отправить локальную роль

### В `syncNow`:
1. Если `!inRemote && remoteData == null && !isFirstSync`: семья удалена → отключить синк, очистить данные
2. Если `!inRemote && remoteData != null`:
   - Если `alreadyCleared`: показать сообщение, НЕ отключать синк
   - Иначе: очистить данные, установить PENDING, добавить в `deletedMembers`, НЕ отключать синк
3. Если `inRemote && remoteRole == PENDING && localRole == PENDING`: не импортировать данные
4. Если `inRemote && remoteRole != PENDING && localRole == PENDING`: принять роль, начать импорт

### В `mergeMembers`:
1. Если `id in deletedMembers`: НЕ добавлять обратно (даже если есть в remote)
2. Если `isMemberWriteAllowed && l == null && r != null`: админ удалил локально → НЕ добавлять из remote
3. **КРИТИЧНО: Приоритет remote-админа** - Если `r.role == ADMIN`: всегда сохранять (защита от случайного удаления админа)
4. **КРИТИЧНО: Запрет записи members для не-админов** - Не-админы НЕ могут писать в members (контролируется через `isMemberWriteAllowed` на клиенте и правилами Firestore в продакшене)

## Лимит на единственного админа

### Проблема
В семье должен быть ровно один ADMIN. Без этого ограничения возможны:
- Несколько админов (конфликты управления)
- Потеря админа (семья остается без управления)
- Конфликты при синхронизации

### Реализация

#### 1. В UI (SettingsViewModel.approveMember)
- При попытке одобрить участника как ADMIN проверяется наличие других ADMIN
- Если уже есть ADMIN, роль откатывается на CHILD и показывается ошибка
- **Реализация:** Проверка `currentMembers.any { it.role == MemberRole.ADMIN && it.id != member.id }`

#### 2. В publishSelfMember
- Перед отправкой себя как ADMIN проверяется наличие других ADMIN в remote
- Если в remote уже есть ADMIN, отправка блокируется
- **Реализация:** Проверка `remoteData.members.filter { it.role == MemberRole.ADMIN.name && it.id != member.id }`

#### 3. В mergeMembers
- После merge проверяется количество ADMIN в результате
- Если больше одного - оставляется только первый (по ID для детерминированности)
- Если нет ни одного, но семья существует - восстанавливается ADMIN из remote
- **Реализация:** Проверка `result.count { it.role == MemberRole.ADMIN.name }`

#### 4. В uploadSnapshot (перед загрузкой)
- Перед загрузкой проверяется количество ADMIN в merged данных
- Если больше одного или ноль (при существующей семье) - загрузка блокируется
- **Реализация:** Проверка `uploadMerged.members.count { it.role == MemberRole.ADMIN.name }`

#### 5. В правилах Firestore
- **ОГРАНИЧЕНИЕ:** Правила Firestore не могут эффективно проверить все документы в коллекции
- Проверка выполняется только для базовых случаев (создание первого участника)
- Полная проверка "ровно один ADMIN" выполняется на клиенте

**Важность:**
- Предотвращает конфликты управления семьей
- Гарантирует, что семья всегда имеет администратора
- Защищает от потери доступа при синхронизации

## Важные замечания по реализации

### Обработка ошибок и исключений

**В `syncNow`:**
- Все исключения обрабатываются через `try-catch-finally`
- `isSyncing` **ВСЕГДА** сбрасывается в `false` в блоке `finally` (строка 861)
- Это гарантирует, что UI всегда получит корректное состояние синхронизации
- Ошибки сохраняются в `syncSettingsDataStore.setLastError()` для отображения пользователю

**Типы ошибок:**
- `PERMISSION_DENIED` / `UNAUTHENTICATED`: отключить синк (нет доступа)
- Сетевые ошибки / таймауты: сохранить `hasPendingChanges`, показать ошибку, но не отключать синк
- Ошибки загрузки: показать ошибку, но не отключать синк (временные проблемы)

**Реализация:**
```kotlin
try {
    // ... логика синхронизации ...
} catch (e: FirebaseFirestoreException) {
    // ... обработка ошибок ...
} catch (e: Exception) {
    // ... обработка ошибок ...
} finally {
    _state.value = _state.value.copy(isSyncing = false)  // ВСЕГДА сбрасывается
}
```

**КРИТИЧНО: Различение сетевых ошибок от удаления семьи:**
- `remoteMissing = true` только если запрос успешен, но данных нет (реальное удаление)
- Сетевые ошибки и таймауты НЕ трактуются как удаление семьи
- Проверка: `remoteMissing && !isNetworkError && !isTimeoutError`
- Это предотвращает ложные срабатывания при нестабильной сети

### Приоритет remote-админа в mergeMembers

**Реализация (строка 1068-1070):**
```kotlin
if (r.role == MemberRole.ADMIN.name) {
    Timber.d("mergeMembers: Preserving ADMIN from remote: %s", r.id)
    return@mapNotNull r
}
```

**Логика:**
- Админ из remote **ВСЕГДА** сохраняется в результате merge
- Это защита от случайного удаления админа при конфликтах
- Даже если админ был удален локально, он восстанавливается из remote
- Исключение: если админ в `deletedMembers` (явно удален админом) - не восстанавливается

**Важность:**
- Предотвращает потерю доступа к семье при конфликтах синхронизации
- Гарантирует, что хотя бы один админ всегда присутствует в семье

### Запрет записи members для не-админов

**Реализация в `uploadSnapshot` (FirestoreBackendApi, строка 223):**
```kotlin
if (isMemberWriteAllowed) {
    syncCollection(MEMBERS_COLLECTION, snapshot.members, ExportMember::id)
}
```

**Логика:**
- Параметр `isMemberWriteAllowed` контролирует запись в коллекцию `members`
- Если `isMemberWriteAllowed = false`, участники **НЕ добавляются** в batch для записи
- Только админ может записывать/обновлять/удалять участников через `uploadSnapshot`
- Не-админы могут обновить только свою запись через `publishSelfMember` (с ограничениями)

**Важность:**
- Предотвращает несанкционированное изменение состава семьи
- Защищает от случайного удаления участников не-админами
- В продакшене правила Firestore дополнительно защищают на уровне сервера

**Двойная защита:**
1. Клиентская логика (`isMemberWriteAllowed`) - блокирует на уровне кода
2. Правила Firestore (в продакшене) - блокируют на уровне сервера

## Резюме для продакшена

### Обязательные действия перед релизом:

1. **Применить строгие правила Firestore** (см. раздел "Рекомендуемые правила для продакшена")
   - Без этого система уязвима для несанкционированного доступа
   - Правила должны быть применены ДО первого релиза
   - **ВАЖНО:** Правила не проверяют "ровно один ADMIN" (слишком дорого), проверка на клиенте

2. **Проверить клиентскую логику:**
   - `isMemberWriteAllowed` правильно определяется для всех ролей
   - `uploadSnapshot` не записывает members для не-админов
   - `mergeMembers` сохраняет remote-админа при конфликтах
   - **КРИТИЧНО:** Проверка на единственного админа работает во всех местах:
     - `approveMember` - блокирует создание второго ADMIN
     - `publishSelfMember` - проверяет remote перед отправкой ADMIN
     - `mergeMembers` - исправляет множественных ADMIN
     - `uploadSnapshot` - блокирует загрузку с множественными ADMIN

3. **Проверить обработку ошибок:**
   - `isSyncing` всегда сбрасывается в `finally`
   - Ошибки корректно отображаются пользователю
   - Синк не отключается при временных проблемах сети
   - **КРИТИЧНО:** Различение сетевых ошибок от удаления семьи (не ложные срабатывания)

4. **Проверить защиту от возврата удаленных участников:**
   - `deletedMembers` список правильно управляется
   - Удаленные участники не восстанавливаются из remote
   - Правила Firestore не позволяют второму админу вернуть удаленного (но это контролируется клиентом)

5. **Тестирование:**
   - Создание новой семьи (ADMIN)
   - Присоединение к семье (PENDING)
   - Одобрение/отклонение заявки
   - Попытка создать второго ADMIN (должна блокироваться)
   - Удаление участника
   - Повторная подача заявки после отклонения
   - Синхронизация в различных состояниях
   - Синхронизация при нестабильной сети (не должно быть ложных удалений семьи)
