# Синхронизация данных в FamilyHub

## Текущее состояние (MVP)

В текущей версии MVP **синхронизация между устройствами не реализована**. Все данные хранятся локально в Room базе данных на каждом устройстве.

### Архитектура данных

```
UI Layer (Compose)
    ↓
ViewModel
    ↓
Repository (Local)
    ↓
Room DAO
    ↓
SQLite Database (локально)
```

Все операции выполняются только с локальной БД. Каждое устройство имеет независимую копию данных.

---

## Архитектура для будущей синхронизации (v1)

Архитектура спроектирована так, чтобы легко добавить синхронизацию в будущем:

### Текущая структура (готова к синхронизации)

```
┌─────────────────────────────────────────┐
│           Domain Layer                  │
│  (чистые модели без аннотаций Room)    │
│  Task, ShoppingItem, FamilyEvent...     │
└─────────────────────────────────────────┘
              ↑ ↓
┌─────────────────────────────────────────┐
│         Repository Layer                │
│  (маппинг Entity ↔ Domain)             │
│  TaskRepository, ShoppingRepository... │
└─────────────────────────────────────────┘
              ↑ ↓
┌─────────────────────────────────────────┐
│         Data Source Layer               │
│  ┌──────────────┐  ┌──────────────┐    │
│  │ Local (Room) │  │ Remote (API)│    │
│  │    DAO       │  │  (future)   │    │
│  └──────────────┘  └──────────────┘    │
└─────────────────────────────────────────┘
```

### План реализации синхронизации

1. **Создать Remote Data Source**
   - API интерфейсы для работы с облачным сервером
   - Реализация через Firebase/Backend API
   - Модели для сетевых запросов/ответов

2. **Обновить Repository Pattern**
   - Repository будет работать с несколькими источниками данных
   - Логика выбора источника (локальный vs облачный)
   - Стратегия синхронизации (push/pull)

3. **Механизм синхронизации**
   - Фоновая синхронизация через WorkManager
   - Конфликт-резолюшн при одновременных изменениях
   - Очередь изменений для офлайн режима

## Варианты реализации синхронизации

### Вариант 1: Firebase Realtime Database / Firestore

**Плюсы:**
- Простая интеграция
- Реалтайм синхронизация
- Автоматическая обработка офлайн режима

**Минусы:**
- Зависимость от Firebase
- Стоимость при росте трафика

**Архитектура:**
```
Repository
    ├── LocalDataSource (Room)
    └── RemoteDataSource (Firebase)
         └── SyncManager (координация)
```

### Вариант 2: REST API + Custom Backend

**Плюсы:**
- Полный контроль над данными
- Гибкость в реализации

**Минусы:**
- Нужно поддерживать backend
- Больше кода для синхронизации

### Вариант 3: Firebase + Cloud Firestore (рекомендуется для v1)

**Структура:**
- Каждая семья = отдельный документ/коллекция
- Каждый тип данных = подколлекция
- Timestamp для отслеживания изменений

## Рекомендуемый подход для v1

### 1. Структура данных в Firebase

```
families/{familyId}/
    ├── members/
    │   └── {memberId}
    ├── tasks/
    │   └── {taskId}
    ├── shopping/
    │   └── {itemId}
    ├── events/
    │   └── {eventId}
    └── scores/
        └── {userId}_{weekStart}
```

### 2. Механизм синхронизации

```kotlin
// Псевдокод архитектуры
class TaskRepository(
    private val localDataSource: TaskLocalDataSource,
    private val remoteDataSource: TaskRemoteDataSource,
    private val syncManager: SyncManager
) {
    fun getAllTasks(): Flow<List<Task>> {
        // Сначала показываем локальные данные
        return localDataSource.getAllTasks()
            .flatMapLatest { localTasks ->
                // Параллельно синхронизируем с сервером
                syncManager.syncTasks()
                flowOf(localTasks)
            }
    }
    
    suspend fun upsertTask(task: Task) {
        // Сохраняем локально сразу
        localDataSource.upsert(task)
        
        // Добавляем в очередь синхронизации
        syncManager.queueUpdate(task)
    }
}
```

### 3. Стратегия синхронизации

- **Pull синхронизация**: периодически (каждые 5-10 минут) или при открытии приложения
- **Push синхронизация**: сразу после локальных изменений (если есть интернет)
- **Офлайн очередь**: сохранять изменения локально, синхронизировать когда появится интернет
- **Конфликт-резолюшн**: Last Write Wins или пользователь выбирает

## Текущие возможности для синхронизации

### Что уже готово:

1. ✅ **Разделение Entity и Domain моделей**
   - Entity - для Room (локальное хранение)
   - Domain - чистые модели (можно использовать и для API)

2. ✅ **Repository Pattern**
   - Уже абстрагирует источник данных
   - Легко добавить RemoteDataSource

3. ✅ **Flow для реактивности**
   - UI автоматически обновляется при изменении данных
   - Можно подписаться на изменения из Firebase

## Рекомендации

Для MVP текущая архитектура достаточна. Для v1 можно:

1. Добавить Firebase в проект
2. Создать RemoteDataSource реализации
3. Расширить Repository для работы с несколькими источниками
4. Реализовать SyncManager для координации синхронизации
